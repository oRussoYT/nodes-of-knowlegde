# M6.4 — Relationship Engine: Relationships as Historical Narratives (implementation)

## Status

Implemented in this milestone. This is the fourth production engine of the
Digital Scientific Biography, after identity+narrative (M6.1), Timeline (M6.2),
and Participation (M6.3). It is a complete, database-backed vertical slice for
**authenticated authorized reading** of the historically meaningful bonds that
shaped a scientific life -- who influenced this person, whom they mentored, with
whom they collaborated -- first manifested inside the Scientific Biography,
architected so the same model extends without redesign to other entity pairings
(person<->institution, institution<->institution, ...) once those entities
exist. The universal Entity Engine, Institution Engine, Contribution Engine,
Historical Records, Knowledge Network visualization, and any inference/AI
librarian remain deliberately deferred.

Validation is the local development environment's responsibility (see
"Required local validation" below); this document does not claim any command
has passed.

## What M6.4 implements

- **Relationships as bonds between entities (CC1).** `public.relationships` --
  ONE canonical record per bond (never mirror rows): source + target person +
  kind + optional curated narrative + the shared temporal model + provenance.
  Distinct from Participation (bounded belonging) and Events (something that
  happened).
- **Directionality and reciprocity as data.** `public.relationship_kinds`
  declares per kind whether it is directional and the role each end plays
  (singular + plural). Directional kinds name two roles (Mentor/Student);
  symmetric kinds repeat one (Collaborator).
- **One record, both pages, inverse labels.** `public.get_person_relationships`
  projects the same record onto either person with that person's perspective --
  a mentorship reads "under Students" on the mentor's page and "under Mentors"
  (the inverse label) on the student's page, no duplication.
- **Canonical reciprocal storage, enforced.** A denormalized `is_directional`
  (forced to match its kind by a composite FK) lets a CHECK require symmetric
  bonds to be stored in canonical order (source < target), so `(A,B)` and
  `(B,A)` can never both exist; a `unique(kind, source, target)` blocks exact
  duplicates; a CHECK forbids self-relationships.
- **Relationship kinds as a Node-neutral vocabulary.** Seeded with 11 generic
  kinds; institution/project/family kinds are added as data / deferred.
- **The shared Many-Clocks temporal + provenance kernels** (`src/features/
  shared`) -- reused, not duplicated: exact/month/year/decade precision, circa,
  uncertainty, ranges, ongoing, unknown; and the source/verification vocabulary
  with identical labels to every other engine.
- **An optional curated narrative**, distinct from the facts, never
  auto-generated; a blank narrative is rejected and a missing one is honestly
  absent.
- **A reusable relationships feature module** (`src/features/relationships/`):
  `types`, `parse` (fail-closed per relationship), `derive` (grouping by the
  counterpart's role), `copy` (Node-neutral), `read`, and calm museum-quality
  components (`Relationships`, `RelationshipGroup`, `RelationshipEntry`,
  `RelationshipPeriod`, `RelationshipNarrative`, `RelationshipProvenance`).
- **Scientific Biography integration.** Relationships render inside
  `/people/[personId]`, after Participation, replacing the M6.1 reserved
  Relationships placeholder.
- **Honest empty / incomplete states.** No relationships -> a dignified
  absence, never suggested/inferred connections; unknown dates and provisional/
  disputed bonds stay visible and honestly labelled.
- **Tests**: pgTAP (kind + directionality FK, self-relationship policy,
  canonical reciprocal storage, duplicate prevention, blank-narrative rejection,
  temporal + provenance invariants, authorization, deny-by-default reads, BOTH-
  SIDE projection with inverse labels, merged-counterpart omission, chronological
  ordering, empty/merged/nonexistent), Vitest (parse/derive/copy, inverse-label
  grouping, symmetric vs directional), Playwright (both-side inverse labels for
  directional and symmetric bonds, narrative present/absent, temporal states,
  disputed provenance, provenance accessible name + keyboard, grouping,
  responsive 375px, light/dark, overflow, duplicate ids, console, axe).

## How it maps to the constitutional documents

- **Entity / Assertion / Provenance**: each bond is an Assertion between two
  Entities, carrying its own `source_type`/`verification_status`; a row never
  implies truth and is never inferred.
- **Relationships are historical narratives, not a social graph**: the reading
  answers "who shaped this life, and whose lives did this person shape?" through
  role, period, curated narrative, and provenance -- no edges, avatars grids,
  follower counts, suggestions, or graph widgets.
- **CC1**: a bond between entities, never Participation (bounded belonging).
- **Event boundary**: a bond that may persist and change over time, never an
  Event; Events may mark its stages.
- **Many-Clocks**: the shared temporal kernel keeps precision, approximation,
  uncertainty, interval, ongoing, and unknown distinct.
- **Dignity across roles**: grouped by the counterpart's role and ordered by
  earliest involvement -- never ranked by prestige; a mateiro, technician,
  field assistant, student, or community collaborator is treated exactly as a
  senior scientist.
- **Node Independence**: `relationships`, `relationship_kinds`,
  `get_person_relationships`, and every component carry no PDBFF assumption;
  kinds are generic data; the only Node identity remains `SITE_NAME`.

## The three engines, read on one page

Timeline is a spine through **time** (what happened, when, grouped by decade).
Participation is a map of **belonging** (where and how this person belonged,
grouped by organization). Relationships is a map of **bonds** (who shaped this
life and whose lives this person shaped, grouped by the counterpart's role --
"Mentors", "Students", "Collaborators"). Reading the page top to bottom, the
distinctions are immediate, with no explanatory bureaucracy.

## Directionality, reciprocity, and inverse labels

A relationship kind is either directional (source and target play different
roles: mentor->student, advisor->advisee, interviewer->interviewee,
predecessor->successor) or symmetric (both ends play the same role:
collaborators, field partners, correspondents). The single canonical record
stores source and target; `get_person_relationships` returns, for the viewed
person, the counterpart's role -- which is the target role when the viewed
person is the source, and the source role (the INVERSE) when they are the
target. Symmetric records are stored in canonical order so a reciprocal bond is
never duplicated. The UI groups by the counterpart's plural role label, so the
same record files under the correct, inverse heading on each person's page.

## Privacy and ethics

Reading stays behind the existing authenticated, authorized boundary (no new
public surface, no new personal data exposed by default -- only the
counterpart's display name, already shown for people elsewhere). Provisional and
disputed bonds are shown calmly and labelled honestly; nothing fabricates
certainty. Merged counterparts are omitted; a merged/nonexistent subject
returns null. Family relationship kinds are deliberately NOT seeded pending
governance, and the engine performs no inference. Open governance questions
(below) are documented, not resolved in code.

## Read-model architecture

A separate `get_person_relationships` read function, composed at the biography
page alongside `get_person_biography`/`get_person_timeline`/
`get_person_participation` -- not an extension of `get_person_biography` into a
monolith. This preserves authorization consistency, provenance, independent
capability evolution, fail-closed parsing (`src/features/relationships/
parse.ts`), Node Independence, and both-side projection from one record.

## Explicitly deferred (not in M6.4)

The universal Entity Engine and polymorphic source/target; the Institution and
Contribution engines; other entities' relationship rosters; a Knowledge Network
visualization or graph traversal UI; relationship recommendations / inferred
relationships / an AI librarian; a client relationship-authoring or editorial
workflow; a public (unauthenticated) surface; relationship revision/history;
family and other ethically-sensitive kinds (governance); search ranking; any
social features (likes, follows, endorsements, connections); federation; the
NetPDBFF -> Nodes-of-Knowledge branding migration; M6.5.

## Extension points for later engines

- **Endpoints**: the typed `source_person_id`/`target_person_id` generalize (by
  additive migration) to other entity types behind the same read-model
  contract -- where the Institution/Contribution engines attach.
- **Shared kernels**: `src/features/shared/temporal.ts` and `provenance.ts`
  remain the single home every engine dates and provenances through.
- **Vocabulary**: `relationship_kinds` rows are added/retired/translated as
  data; directionality and labels travel with the row.
- **Suggestion surface**: any future inference becomes a librarian *suggestion*
  layer, never written as a confirmed relationship.

## Divergence flagged for review

As in M6.2/M6.3, the two new tables (`relationships`, `relationship_kinds`)
carry explicit `grant select, insert, update, delete ... to service_role`. They
remain RLS-enabled deny-by-default with no client GRANT/policy, so client read
access is only through `get_person_relationships`; the grant enables the trusted
server-side write path (no client authoring path in M6.4) and per-test
disposable Playwright fixtures. Consistent with the M3.1 all-tables pattern and
called out here and in ADR-0014 for explicit review.

## Open governance / legal questions (unresolved by code)

- **Family and other ethically-sensitive relationship kinds** (living
  relatives, vulnerable individuals, power asymmetries, private correspondence):
  deferred pending governance; not seeded.
- **Living-person relationships and a future public surface**: the conservative
  authenticated-only boundary is kept; a public relationship surface is deferred
  with the M6.V public-record policy (G1).
- **Withdrawal / correction / conflicting institutional accounts**: the
  provisional/disputed vocabulary and the single canonical record make these
  representable, but the editorial workflow and dispute governance are deferred.

## Required local validation

Run on a machine with the toolchain (Docker + Supabase local). The DB layer
must be reset and types regenerated before typecheck/build, because new code
references the new function/table types:

```
npm run supabase:reset       # apply the new relationship migration
npm run supabase:test        # pgTAP (relationships.test.sql)
npm run supabase:types       # regenerate src/types/database.types.ts
npm run test                 # Vitest (relationships + participation + timeline + biography suites)
npm run typecheck
npm run lint
npm run build
npm run test:e2e             # Playwright (relationships.spec.ts)
npm audit
npm audit --omit=dev
git diff --check
```

Report failures back; iterate until green. No command above has been run in
the authoring environment.
