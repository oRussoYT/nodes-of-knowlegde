# M6.3 — Participation Engine: Bounded Belonging (implementation)

## Status

Implemented in this milestone. This is the third production engine of the
Digital Scientific Biography, built on the M6.1 identity + narrative foundation
and the M6.2 Timeline. It is a complete, database-backed vertical slice for
**authenticated authorized reading** of a person's bounded belonging through
time -- where they belonged, in what capacity, for what period, under what
evidence -- first manifested inside the Scientific Biography, architected so
the same model later serves any Node and (via a sibling read function) other
entities' rosters unchanged. The Institution, Relationship, and Legacy engines
remain deliberately deferred and reserved as honest extension points.

Validation is the local development environment's responsibility (see
"Required local validation" below); this document does not claim any command
has passed.

## What M6.3 implements

- **Participation as bounded belonging.** `public.participations` = person +
  organization + capacity + a dated period + its own provenance and
  verification. CC1: not authorship, ownership, provenance, causation, or
  relationship (ADR-0013).
- **A minimal belonging-target entity.** `public.organizations` (identity
  only: `name`, `short_name`) -- the smallest durable "where," deliberately
  NOT the Institution Engine.
- **Capacities as data.** `public.participation_capacities`, seeded with 13
  generic, Node-neutral capacities -- a PDBFF *mateiro* is added as a data row,
  never hardcoded (`docs/controlled-vocabularies.md`).
- **Concurrent and sequential belonging, first-class.** No uniqueness
  constraint on `participations`; a person may hold many capacities/periods at
  one organization and belong to several organizations at once (CLAUDE.md:
  "never model participation as a single date range or a single role").
- **A per-subject canonical read model.** `public.get_person_participation(uuid)`
  -- a `SECURITY DEFINER` function returning a provenance-bearing set of
  participations (organization + capacity resolved), ordered chronologically,
  undated last; the single new read path over the still-locked tables.
- **A shared temporal + provenance kernel.** `src/features/shared/temporal.ts`
  and `src/features/shared/provenance.ts` -- the Many-Clocks temporal model and
  the provenance vocabulary/labels, now shared by Timeline and Participation
  (and every later engine). Timeline re-exports them under its historical names
  via behavior-preserving shims; its public surface and tests are unchanged.
- **A reusable participation feature module.** `src/features/participation/` --
  `types`, `parse` (fail-closed per participation), `derive` (grouping by
  organization), `copy` (Node-neutral), `read`, and calm museum-quality
  components (`Participation`, `AffiliationGroup`, `ParticipationEntry`,
  `ParticipationPeriod`, `ParticipationProvenance`).
- **Scientific Biography integration.** Participation renders inside
  `/people/[personId]`, after the Timeline, replacing the M6.1 reserved
  Participation placeholder with the real engine.
- **Honest empty / incomplete / uncertain states.** An empty record is a
  dignified absence; an undated belonging is kept and read as "Date unknown";
  approximate periods read as "c. …"; concurrent and open-ended belongings are
  shown as they are.
- **Tests**: pgTAP (belonging/temporal CHECK invariants, FK integrity,
  authorization, deny-by-default reads, chronological content, organization +
  capacity resolution, provenance, empty/merged/nonexistent), Vitest
  (derive/parse/copy), Playwright (reading flow, capacities, temporal states,
  organization grouping, concurrent belonging, provenance disclosure,
  responsive 375px, light/dark, keyboard, axe, quality).

## How it maps to the constitutional documents

- **Entity / Assertion / Provenance**: the participation is an Assertion
  projecting a person onto an organization, carrying its own
  `source_type`/`verification_status` -- no bare trusted fact.
- **Bounded belonging, not administrative structure**: it records where/how/
  when a person belonged; it is not an org chart, HR record, or roster
  management surface. It reads as institutional memory.
- **CC1**: an Event is not a Participation and a Participation is not
  authorship, ownership, provenance, causation, or relationship -- the model
  carries none of those.
- **CC2**: no dataset/repository behavior.
- **Many-Clocks**: the SHARED temporal kernel keeps precision, approximation,
  uncertainty, interval, open-endedness, and unknown distinct; the read model
  is one function per subject clock.
- **Honesty as design material**: honest absence, honest "date unknown",
  honest circa/uncertain distinctions, calm `provisional`/`disputed`.
- **Museum quality**: disciplined typography, measure, whitespace, restrained
  emphasis, accessible focus, light/dark, mobile reading.
- **Node Independence**: `participations`, `organizations`,
  `participation_capacities`, `get_person_participation`, and every component
  carry no PDBFF assumption; capacities are generic data (a *mateiro* is a
  Node's data row), and the only Node identity remains `SITE_NAME`.

## Timeline vs. Participation — why the page reads them differently

The Timeline is a spine through **time**: what happened, when, grouped by
decade. Participation is a map of **belonging**: where and how this person
belonged, grouped by **organization**. Same shared temporal kernel dates both,
but the Timeline leads each entry with its date and groups by decade, while
Participation leads each entry with its **capacity**, sits it under its
**organization**, and shows the **period** beneath -- so reading the page, the
distinction is immediate: "what happened" then "where did they belong."

## Explicitly deferred (not in M6.3)

The Institution Engine (organization timelines, hierarchy, provenance,
enrichment, an institution read experience); other entities' participation
rosters (`get_organization_participation`, project teams) beyond the
architecture that enables them; a client participation-authoring / editorial
workflow (participations are service-role/admin-authored, as narrative and
events are); a public (unauthenticated) surface; participation revision/
history; the Relationship and Legacy engines; multi-Node federation;
AI-generated or inferred belonging; the NetPDBFF -> Nodes-of-Knowledge branding
migration.

## Extension points for later engines

- **Shared kernels**: `src/features/shared/temporal.ts` and
  `provenance.ts` are the single home every later clock dates and provenances
  through -- no engine re-implements them.
- **Belonging target**: `organizations` is where the Institution Engine
  attaches (timelines via a sibling `organization_events` join, enrichment,
  provenance) without changing the participation model.
- **Other rosters**: `get_person_participation` is the template for a sibling
  `get_organization_participation` (who belonged to an organization) and other
  subject rosters.
- **Vocabulary**: `participation_capacities` rows are added/retired/translated
  as data; a Node's own capacities need no code change.

## Divergence flagged for review

As in M6.2/ADR-0012, the three new tables (`participations`, `organizations`,
`participation_capacities`) carry explicit `grant select, insert, update,
delete ... to service_role`. They remain RLS-enabled deny-by-default with no
client GRANT/policy, so client read access is only through
`get_person_participation`; the grant enables the trusted server-side write
path (there is no client participation-authoring path in M6.3) and per-test
disposable Playwright fixtures. Consistent with the M3.1 all-tables pattern and
called out here and in ADR-0013 for explicit review.

Additionally, M6.3 refactors M6.2's temporal formatter and provenance labels
into `src/features/shared` and re-points the Timeline at them via
behavior-preserving re-export shims (`src/features/timeline/temporal.ts`,
`types.ts`, `derive.ts`). This touches M6.2 files by design (to avoid a
duplicated "parallel architecture") and is guarded by the unchanged M6.2 unit
tests, which still exercise the same functions through the Timeline's exports.

## Required local validation

Run on a machine with the toolchain (Docker + Supabase local). The DB layer
must be reset and types regenerated before typecheck/build, because new code
references the new function/table types:

```
npm run supabase:reset       # apply the new participation migration
npm run supabase:test        # pgTAP (participation.test.sql)
npm run supabase:types       # regenerate src/types/database.types.ts
npm run test                 # Vitest (participation + timeline + biography suites)
npm run typecheck
npm run lint
npm run build
npm run test:e2e             # Playwright (participation.spec.ts)
npm audit
npm audit --omit=dev
git diff --check
```

Report failures back; iterate until green. No command above has been run in
the authoring environment.
