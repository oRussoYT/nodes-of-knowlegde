# M6.5 — Institution Engine: Institutions as Historical Actors (implementation)

## Status

Implemented in this milestone. The fifth production engine of the Digital
Scientific Biography, after identity+narrative (M6.1), Timeline (M6.2),
Participation (M6.3), and Relationship (M6.4). It is a complete, database-backed
vertical slice for **authenticated authorized reading** of an institution as a
historical ACTOR -- how it came into being, changed through time, organized
people, and preserved memory -- delivered as a first-class Institution page. It
extends the M6.3 `organizations` entity ADDITIVELY (no parallel table, M6.3
Participation unchanged), reuses canonical Events and Participations by
projection, and reuses the shared temporal/provenance kernels. The universal
Entity Engine, institution<->institution Relationships, the Contribution Engine,
Historical Records ingestion, and any Node administration remain deferred.

Validation is the local development environment's responsibility (see "Required
local validation" below); this document does not claim any command has passed.

## What M6.5 implements

- **Additive institutional identity on `organizations`**: `organization_type`
  (FK to a vocabulary), `status` (historical/operational state), founding &
  closure temporal, `location`, `website`, and the record's own provenance --
  all defaulted so M6.3 rows/Participation stay valid.
- **`organization_types`** -- Node-neutral institution-type vocabulary (19 seeded).
- **`organization_names`** -- historically valid / former / alternative /
  acronym / Indigenous / local / translated names, each with form, language,
  type, the period used, provenance, verification (not disposable synonyms).
- **`organization_external_identifiers`** -- ROR/Wikidata/ISNI/VIAF/GRID/
  national/archival support; `unique(scheme, value)`; interoperability, never
  authority, never auto-merge.
- **`organization_narrative`** -- curated history in facets (introduction /
  overview / significance / legacy), one current per facet, provenance-bearing.
- **`organization_events`** -- projects a canonical Event onto an institution
  timeline WITHOUT duplication (mirrors `person_events`; Many-Clocks).
- **Three bounded reads** -- `get_organization`, `get_organization_timeline`,
  `get_organization_participation` (SECURITY DEFINER), composed at the page.
- **The Institution page** (`/institutions/[organizationId]`): identity header,
  introduction (+ overview), names, timeline (the reused M6.2 Timeline),
  people & participation (grouped by capacity, equal dignity), honest reserved
  Relationships/Contributions/Historical-records surfaces, significance, and
  legacy -- with honest empty/absence states throughout.
- **Discovery**: the person biography's Participation links each organization
  name to its Institution page.
- **Tests**: pgTAP (identity/vocab/name/identifier/narrative constraints, Event
  projection without duplication, Participation projection, historical/closed/
  nonexistent readability, empty states, authorization, deny-by-default),
  Vitest (parse/derive/copy, period derivation, participation grouping), and
  Playwright (identity, narrative present/absent, historical institution,
  timeline, participation, cross-perspective consistency + discovery link,
  provenance accessible name, keyboard, responsive, themes, overflow, dup ids,
  console, axe).

## How it maps to the constitutional documents

- **Two clocks**: institutions endure and transform; the founding/closure
  temporal + status + projected Events + historical names make both the
  endurance and the remaking visible.
- **Historical actor, not a corporate profile**: no logo requirement, no
  metrics, no marketing; identity, history, people, and evidence.
- **CC1 kept**: an Institution (actor) is not Participation (belonging) and not
  an Event (something that happened); a Relationship is a bond -- none collapsed.
- **CC2**: knowledge-history, not raw datasets; Contributions/Records are
  reserved as knowledge-making history, not a file repository.
- **Provenance-first**: every institutional assertion (the record, each name,
  identifier, narrative facet, projected event, participation) carries source +
  verification; a row never implies truth.
- **Equal dignity**: participation grouped by capacity, ordered historically,
  never by prestige; a mateiro/technician/field assistant reads like a director.
- **Sovereignty without monopoly on truth**: per-assertion provenance lets
  self-description, archival evidence, and third-party accounts coexist; no
  single "owner of truth" is assigned in code (governance deferred).
- **Node Independence**: `organizations`, the vocabularies, and every component
  carry no PDBFF assumption and work for a university, museum, archive, field
  station, Indigenous organization, community association, or a historical
  institution that no longer exists.

## Read-model architecture

Three bounded SECURITY DEFINER reads, composed at the page (not a monolith):
`get_organization` returns the institution's own record + historical names +
external identifiers + narrative facets; `get_organization_timeline` projects
canonical Events (same shape as `get_person_timeline`, reused via an adapter);
`get_organization_participation` projects the SAME M6.3 Participation records
from the institution's perspective. Each is `auth.uid()`-gated, `search_path`
pinned, `EXECUTE` to `authenticated` only; the tables stay locked deny-by-default.

## Institutional identity, names, and external identifiers

The canonical CURRENT name is `organizations.name`; `organization_names` holds
former/alternative/acronym/Indigenous/local/translated names, each with its own
period and provenance. `organization_external_identifiers` preserves external
ids for interoperability (`unique(scheme, value)`), never as authority and never
auto-merging records (duplicate resolution stays governed).

## Timeline and Participation projection (no duplication)

`organization_events` projects a canonical `public.events` row onto an
institution timeline -- the same Event may also appear on a person timeline
without a contradictory copy. `get_organization_participation` reads the SAME
`participations` rows from the institution side, so one Participation appears on
the person's biography (as belonging) AND on the institution's page (as human
history), grouped by capacity with equal dignity.

## Transformation and succession boundaries

Founding/closure temporal + `status` + projected Events + historical names carry
transformation; a single mutable field does not. Predecessor/successor
Relationships and institution<->institution partnerships are DEFERRED (M6.4 is
person<->person; see the additive path in ADR-0015). A current institution never
erases a predecessor; a successor does not automatically inherit a predecessor's
assertions; historical continuity may be verified, provisional, disputed, or
unresolved.

## Relationship boundary and limitations (what M6.5 can and cannot represent)

Representable now: a person's belonging to an institution (Participation,
projected both ways); an institution's own historical names, external
identifiers, timeline of projected Events, and curated narrative.
NOT representable yet: institution<->institution relationships (partnership,
merger-as-relationship, predecessor/successor as a canonical bond) -- reserved
honestly on the page. The additive path: entity-typed relationship endpoints (or
a sibling institution-relationship table) behind the same read-model contract,
without redesigning M6.4.

## Place, sovereignty, and sensitive history

`location` is a single free-text field at the granularity the steward chooses --
no coordinates, no implied territorial ownership, and Indigenous territory is not
reduced to a field. Per-assertion provenance is the foundation for multiple,
possibly conflicting accounts (self-description, archival evidence, third-party
scholarship, oral history, community account) without collapsing disagreement
into false consensus; the governance that distinguishes and adjudicates these is
documented as deferred. The engine sanitizes nothing and fabricates no
accusatory copy; it preserves complex histories as provenance-bearing assertions.

## Explicitly deferred (not in M6.5)

The universal Entity Engine and polymorphic endpoints; institution<->institution
canonical Relationships; the Contribution Engine; Historical Records ingestion /
a file repository / collections management / raw datasets; a place/territory
model beyond one free-text location; external-registry reconciliation and
duplicate merging; an institution directory/search; a public (unauthenticated)
surface; client authoring / editorial workflow; the Knowledge Network
visualization; an AI librarian / recommendations; Node administration /
federation / multi-tenancy; an analytics dashboard; the branding migration; M6.6.

## Extension points

- **Relationships**: entity-typed endpoints behind the M6.4 read contract.
- **Contributions / Historical Records**: the reserved sections mark where those
  engines attach, with the documented creator/custodian/rights/provenance shape.
- **Shared kernels**: temporal and provenance remain the single home every
  engine dates and provenances through.
- **Vocabularies**: `organization_types` (and future name/scheme sets) grow as
  data.
- **Predecessor/successor**: projected Events reserve the transformation surface
  until the relationship generalization lands.

## Divergence flagged for review

As in M6.2-M6.4, the new tables carry explicit `grant ... to service_role`; they
remain RLS-enabled deny-by-default with no client GRANT/policy (client read only
via the three functions). The M6.5 additions to `organizations` are additive
with defaults, so M6.3 Participation and its fixtures/pgTAP remain valid -- this
is called out for review. `status` is a CHECK vocabulary (matching the
established stable-state pattern), while `organization_type` is a lookup table
(open taxonomy); this distinction is deliberate and documented.

## Open governance / legal / ethical questions (unresolved by code)

- Sensitive / Indigenous / protected-area locations, and territorial sovereignty
  vs. institutional activity.
- Institutional sovereignty vs. the platform's duty to preserve documented
  criticism, predecessors, community participation, and disputed accounts -- and
  who may correct or dispute which assertions.
- Duplicate resolution / record merging as a governed process (external ids
  never auto-merge).
- A future public (unauthenticated) institution surface (deferred with the M6.V
  public-record policy).

## Required local validation

Run on a machine with the toolchain (Docker + Supabase local). Reset the DB and
regenerate types before typecheck/build:

```
npm run supabase:reset       # apply the new institution migration
npm run supabase:test        # pgTAP (institution.test.sql)
npm run supabase:types       # regenerate src/types/database.types.ts
npm run test                 # Vitest (institution + relationship + participation + timeline + biography suites)
npm run typecheck
npm run lint
npm run build
npm run test:e2e             # Playwright (institution.spec.ts)
npm audit
npm audit --omit=dev
git diff --check
```

Report failures back; iterate until green. No command above has been run in the
authoring environment.
