# M6.2 — Timeline Engine: The Historical Spine (implementation)

## Status

Implemented in this milestone. This is the second production engine of the
Digital Scientific Biography, built on the M6.1 identity + narrative
foundation. It is a complete, database-backed vertical slice for
**authenticated authorized reading** of a person's chronology — the historical
spine — first manifested inside the Scientific Biography but architected so the
same event core serves later subject clocks (institutions, projects, stations,
expeditions, collections, records, species) unchanged. The later engines
(Participation, Relationships, Institution, Legacy) remain deliberately
deferred and reserved as honest extension points.

Validation is the local development environment's responsibility (see
"Required local validation" below); this document does not claim any command
has passed.

## What M6.2 implements

- **Canonical, subject-neutral event model.** `public.events` with a
  structured temporal envelope (`start_date`/`start_precision`,
  `end_date`/`end_precision`, `is_approximate`, `is_ongoing`,
  `date_is_unknown`, `date_is_uncertain`) and CHECK constraints that keep the
  nine temporal states mutually honest — the database refuses to hold a
  dishonest date (ADR-0012).
- **Events as provenance-bearing assertions.** Every event carries
  `source_type` and `verification_status` (the M6.1 provenance/verification
  vocabulary); `provisional`/`disputed` render calmly, never as errors.
- **Event kinds as data.** `public.event_kinds` lookup table, seeded with 18
  generic, Node-neutral kinds — realizing "vocabularies are data, not code"
  (`docs/controlled-vocabularies.md`); no PDBFF category is hardcoded.
- **Subject-neutral projection edge.** `public.person_events` join
  (`person_id`, `event_id`, unique) — an event exists independently of the
  subject it is projected onto, so the same core later serves other clocks.
- **Per-subject canonical read model.** `public.get_person_timeline(uuid)` — a
  `SECURITY DEFINER` function returning a provenance-bearing timeline `jsonb`
  document, ordered chronologically with undated events honestly last; the
  single new read path over the still-locked event tables. One function per
  clock (Many-Clocks), not a monolith.
- **A reusable timeline feature module.** `src/features/timeline/` — `types`,
  `temporal` (the nine-state date formatter: `c.` circa, en-dash intervals,
  "– present", certainty notes), `parse` (fail-closed per event), `derive`
  (decade grouping + undated group), `copy`, `read`, and calm museum-quality
  components (`Timeline`, `TimelinePeriod`, `TimelineEvent`, `TemporalLabel`,
  `EventProvenance`).
- **Scientific Biography integration.** The timeline renders inside
  `/people/[personId]`, replacing the M6.1 reserved Timeline placeholder with
  the real engine.
- **Honest empty / incomplete / uncertain states.** An empty timeline is a
  dignified absence, not an error; undated events are grouped as "Date
  unknown"; overlapping and open-ended events are shown as they are.
- **Accessible period navigation.** Decade period headings appear only when the
  chronology genuinely spans two or more decades — never manufactured
  navigation for a short life-in-knowledge; semantic headings + ordered lists.
- **Tests**: pgTAP (event/temporal CHECK invariants, authorization, deny-by-
  default reads, chronological content, provenance, kind labels, empty/merged/
  nonexistent), Vitest (temporal/derive/parse/copy), Playwright (reading flow,
  temporal states, decade grouping, overlapping, provenance disclosure,
  responsive 375px, light/dark, keyboard, axe, quality).

## How it maps to the constitutional documents

- **Entity / Assertion / Provenance**: the event is an Assertion projected onto
  the person Entity, carrying its own `source_type`/`verification_status` — no
  bare trusted fact.
- **Historical spine, not an activity feed / résumé / date list**: the model
  centers *what happened in the history of knowledge* with honest time, not a
  reverse-chronological stream of recent actions.
- **Many-Clocks**: the temporal model keeps precision, approximation,
  uncertainty, interval, open-endedness, and unknown distinct; the read model
  is one function per subject clock.
- **Honesty as design material**: honest absence, honest "date unknown",
  honest `c.`/uncertain distinctions, calm `provisional`/`disputed`.
- **Museum quality**: disciplined typography, measure, whitespace, restrained
  emphasis, accessible focus, light/dark, mobile reading — not ornament.
- **CC1**: an Event is *not* a Participation — the timeline records that
  something happened at a time; it models no belonging, authorship, production,
  causation, ownership, or object-of-study relation.
- **CC2**: no dataset/repository behavior — a chronology of knowledge-history,
  not raw scientific data.
- **Node Independence**: `events`, `event_kinds`, `person_events`,
  `get_person_timeline`, and every component carry no PDBFF assumption; kinds
  are generic data and the only Node identity remains `SITE_NAME`.

## The period-navigation threshold rule

Decade period groupings (and their headings) are produced **only** when the
dated events span two or more distinct decades. A life-in-knowledge whose
events fall inside a single decade renders as one calm ordered list with no
manufactured period navigation. Undated events are always collected into a
final "Date unknown" group, after all dated periods. This keeps navigation an
honest reflection of the record's real temporal spread rather than decorative
scaffolding.

## Explicitly deferred (not in M6.2)

The Participation engine (belonging/roles) beyond the CC1-respecting extension
points; Relationship, Institution, and Legacy engines; Historical Records
ingestion; other subject clocks (institution/project/station/expedition/
collection/record/species timelines) beyond the architecture that enables
them; a client event-authoring / editorial workflow (events are service-role/
admin-authored, exactly as narrative is); a public (unauthenticated) timeline
surface; event revision/history; multi-Node federation; AI-generated events or
inferred connections; the NetPDBFF -> Nodes-of-Knowledge branding migration.

## Extension points for later engines

- **Event core is subject-neutral**: add a sibling join table (e.g.
  `institution_events`) and a sibling read function (e.g.
  `get_institution_timeline`) to project the *same* `events`/`event_kinds`
  onto a new subject clock — the event model and temporal model do not change.
- **Read model**: `get_person_timeline` is the template for each per-subject
  clock function; `src/features/timeline/parse.ts` / `types.ts` grow with the
  document, `temporal.ts` is shared across all clocks.
- **Vocabulary**: `event_kinds` rows are added/retired/translated as data; new
  kinds need no code change.
- **Provenance / verification**: the shared `source_type`/`verification_status`
  vocabulary is the single place a richer verification workflow attaches.
- **Participation**: when the Participation engine is built, it is a *separate*
  model (bounded belonging), not an extension of `events` — CC1 keeps the two
  distinct; the timeline's projection edge is the pattern, not the participation
  itself.

## Divergence flagged for review

Unlike M6.1's `person_narrative` (deliberately left without a `service_role`
grant), the three M6.2 tables (`events`, `person_events`, `event_kinds`) carry
explicit `grant select, insert, update, delete ... to service_role`. The
tables remain RLS-enabled deny-by-default with no client GRANT/policy, so
client read access is still only through `get_person_timeline`; the grant
exists to let the trusted server-side path write events (no client authoring
path exists in M6.2) and to let the Playwright suite create/tear down per-test
disposable event fixtures via the service role. This follows the M3.1
all-tables pattern ("BYPASSRLS is not enough — service_role also needs explicit
GRANTs") but is a conscious departure from the M6.1 narrative decision, and is
called out here and in ADR-0012 for explicit review.

## Required local validation

Run on a machine with the toolchain (Docker + Supabase local). The DB layer
must be reset and types regenerated before typecheck/build, because new code
references the new function/table types:

```
npm run supabase:reset       # apply the new timeline migration
npm run supabase:test        # pgTAP (timeline.test.sql)
npm run supabase:types       # regenerate src/types/database.types.ts
npm run test                 # Vitest (timeline-temporal/derive/parse/copy)
npm run typecheck
npm run lint
npm run build
npm run test:e2e             # Playwright (timeline.spec.ts)
npm audit
npm audit --omit=dev
git diff --check
```

Report failures back; iterate until green. No command above has been run in
the authoring environment.
