# M6.1 — Scientific Biography Foundation (implementation)

## Status

Implemented in this milestone. This is the first production implementation of
the Digital Scientific Biography. It is a complete, database-backed vertical
slice for **authenticated authorized reading** of a person's Scientific
Biography, with the later engines deliberately deferred and reserved as honest
extension points.

Validation is the local development environment's responsibility (see
"Required local validation" below); this document does not claim any command
has passed.

## What M6.1 implements

- **Canonical read model.** `public.get_person_biography(uuid)` — a
  `SECURITY DEFINER` function returning a provenance-bearing biography `jsonb`
  document; the single new read path over the still-locked `people` /
  `person_narrative` tables (ADR-0011).
- **Narrative as a first-class authored assertion.** `public.person_narrative`
  (deny-by-default, service-role-managed), separate from `people.biography`.
- **A reusable person-biography route + page architecture.**
  `src/app/(protected)/people/[personId]/` (Server Component), composing a
  feature-owned biography module (`src/features/biography/`).
- **Identity header** with dignified portrait fallback, claim/verification
  state, in-memoriam marker, and identity provenance — never implying
  completeness or verification the data lacks; no fabricated descriptor.
- **Introductory narrative** surface: curated narrative, or an honest,
  dignified absence state — never generated, never AI.
- **Provenance surface**: per-fact source + verification, one gesture away
  (a keyboard-operable disclosure), never an audit wall.
- **Honest incomplete states, honest not-found, conservative visibility**
  (exact life dates withheld; authenticated-only).
- **Reserved section architecture** for Timeline, Participation, Scientific
  Contributions, Relationships, Historical Records, Legacy — honest "will
  appear here" locations, not fabricated modules.
- **Tests**: pgTAP (DB invariants, authorization, withholding,
  claimed/unclaimed, honest null), Vitest (parse/derive/copy), Playwright
  (reading flows, states, provenance, responsive, themes, keyboard, axe,
  quality).

## How it maps to the constitutional documents

- **Entity / Assertion / Provenance** (Blueprint's three atoms): the person is
  the Entity; every rendered fact is an Assertion carrying provenance
  (`source_type`, `verification_status`); nothing is a bare trusted fact.
- **Not a profile** (Design Bible): a person record exists independently of an
  account; the page is a read experience, not a self-maintained profile.
- **Honesty as design material**: honest absence, honest not-found, honest
  withholding; provisional/disputed rendered calmly, never as errors.
- **Museum quality**: disciplined typography, measure, whitespace, restrained
  emphasis, accessible focus, light/dark, mobile reading — not ornament.
- **CC1**: no biography fact is modelled as Participation.
- **CC2**: no dataset/repository behavior.
- **Node Independence**: `people`, `person_narrative`, `get_person_biography`,
  `/people/[personId]`, and the components carry no PDBFF assumption; the only
  Node identity is `SITE_NAME` from `src/config/site.ts`.

## Explicitly deferred (not in M6.1)

Full Timeline / Participation / Relationship / Institution / Legacy engines;
Historical Records ingestion; multi-Node federation; recommendations; inferred
connections; AI-generated biographies; semantic search; graph visualization;
raw scientific-data storage; `profile_visibility_settings` and any broad
public-record/publication policy; client editorial workflow beyond
service-role narrative creation; public (unauthenticated) biography reading;
the NetPDBFF -> Nodes-of-Knowledge branding migration.

## Extension points for later M6 engines

- **Read model**: extend `get_person_biography`'s document (new sections) or
  add sibling read functions; `src/features/biography/parse.ts` and
  `types.ts` grow with them.
- **Page**: `RESERVED_SECTION_ORDER` + `BiographySection` mark where the
  Timeline, Participation, Contributions, Relationships, Historical Records,
  and Legacy engines render.
- **Visibility**: the conservative policy in `get_person_biography` is the
  single place a future `profile_visibility_settings` / public-record policy
  attaches.

## Open governance / legal questions (unresolved by code)

- **G1** — default treatment of a living, unregistered person's already-public
  scholarly record vs. protected personal information (governance + LGPD).
  M6.1 stays conservative (authenticated-only; exact dates withheld) and does
  not decide this; a public route is deferred until it is settled.
- **G2** — narrative authorship / editorial authority (governance). M6.1
  creates narrative via service-role only; no editorial UI.

## Required local validation

Run on a machine with the toolchain (Docker + Supabase local). The DB layer
must be reset and types regenerated before typecheck/build, because new code
references the new function/table types:

```
npm run supabase:reset       # apply the new migration
npm run supabase:test        # pgTAP (scientific_biography.test.sql)
npm run supabase:types       # regenerate src/types/database.types.ts
npm run test                 # Vitest (biography-parse/derive/copy)
npm run typecheck
npm run lint
npm run build
npm run test:e2e             # Playwright (scientific-biography.spec.ts)
npm audit
npm audit --omit=dev
git diff --check
```

Report failures back; iterate until green. No command above has been run in
the authoring environment.
